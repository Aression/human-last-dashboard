# Research Agent Workflows

## Objective

Use language models to reduce the cost of finding, organizing, and analyzing evidence while keeping source provenance, uncertainty, and review decisions inspectable.

## Workflow A: discovery

1. Query configured sources using explicit topic and time-window criteria.
2. Store source metadata and retrieval time.
3. Normalize canonical URLs and compute content hashes where possible.
4. Deduplicate by URL, content hash, and semantic similarity.
5. Label each item as a candidate source, not as verified evidence.
6. Preserve source-specific rate limits and retrieval failures.

Output: a source record and a short reason it may be relevant.

## Workflow B: claim extraction

1. Extract atomic claims rather than broad summaries.
2. Label each claim as observed fact, author interpretation, forecast, or speculation.
3. Attach exact source spans, page/section references, or code locations.
4. Extract conditions: model/version, task, benchmark, data, compute, tools, human intervention, and evaluation protocol.
5. Record limitations and what the source does not establish.
6. Reject claims with no inspectable support or retain them as unverified leads.

Output: candidate claims linked to their source and supporting passages.

## Workflow C: verification

1. Confirm that the cited passage supports the claim in context.
2. Check dates, version numbers, units, benchmark splits, and reported baselines.
3. Separate reported results from independently observed results.
4. Search for replications, corrections, benchmark contamination, evaluation leakage, and contradictory findings.
5. Record unresolved discrepancies rather than forcing a conclusion.

Output: reviewed claim and evidence records with explicit status.

## Workflow D: capability mapping

1. Select the narrowest relevant capability and criterion.
2. Compare evidence with the criterion's operational definition.
3. Identify missing requirements and confounders.
4. Propose a state and confidence with a concise rationale.
5. Link both supporting evidence and counterevidence.
6. Submit any stage change to the configured review gate.

Output: a proposed or reviewed, versioned assessment.

## Workflow E: attribution

For an observed capability change, generate multiple plausible explanations. For each explanation, record its mechanism, supporting evidence, contradictory evidence, assumptions, and discriminating tests. Do not present temporal correlation as causation. Preserve alternatives when the evidence does not identify a unique cause.

## Workflow F: forecast tracking

1. Write a falsifiable prediction and resolution date.
2. Define resolution criteria before observing the outcome.
3. Record a probability only when the forecaster can justify its calibration.
4. Preserve the original forecast.
5. Resolve with evidence and explain ambiguous outcomes.
6. Evaluate calibration over a sufficiently large set of resolved forecasts.

## Required output contract

Each analysis artifact should include:
- Summary of the question.
- Observed facts with source references.
- Inferences and assumptions, clearly separated.
- Evidence supporting the conclusion.
- Counterevidence and alternative explanations.
- Confidence and key uncertainty.
- Capability criteria affected, if any.
- Recommended next investigation.
- Model/provider and workflow version, when generated by an LLM.

## Failure handling

- If a source is inaccessible, record the failure; do not fabricate its contents.
- If sources conflict, retain the disagreement and show both source paths.
- If citations cannot be verified, downgrade the claim status.
- If the model output fails schema validation, retry under bounded policy and then quarantine the artifact.
- If a job is interrupted, resume from the last persisted step using idempotent operations.
- If a stage gate fails, retain the proposal and its missing-evidence checklist without changing the accepted assessment.

## Human review

Human review is required for material stage changes, contested claims, high-impact attribution, and publication of conclusions that could be mistaken for established fact. Reviewers should be able to inspect the underlying source without relying on the model's summary.

## Local tooling for Workflow A and dataset upkeep

`tools/evidence-mcp/` implements the mechanical half of Workflow A and a dataset audit, as MCP tools a local agent calls. It covers steps 1-3 and 5 of Workflow A (fetch, store metadata and retrieval time, normalize and hash, label as candidate) and leaves step 4's semantic deduplication and step 6's judgement to the agent.

- `discovery_run` fetches the configured queries and stores each item as a candidate with `provenance: "discovered"` and `source_tier: "lead"`.
- `discovery_triage` records `accept-for-review`, `reject`, or `duplicate` with a reason. It changes candidate status only.
- Promoting an accepted candidate into the dashboard stays a reviewed edit to `data/`, citing the stored candidate id. No tool performs it.
- `quality_audit` reports bookkeeping problems in the dataset and the candidate store with a remediation each. It never edits either.

The tool takes no view on whether a page's content is true, and a passing audit is not a verification of any claim. See [automation.md](automation.md) for the tools, the store layout, and the schedule.
